요구 정의에서 확인한 업무 배경

기획 방향자료의 성격에 맞춰 정산 업무의 검증 흐름을 새로 설계했습니다.

요구 정의부터 정책·화면 설계, 프로토타입 제작, 개발 전달까지 기획했습니다.

처음 발견한 문제입력 후 오류 원인을 다시 찾는 업무

  • 거래처 자료는 이메일·우편·카카오톡으로 내부 실무자에게 전달됐습니다. 실무자가 파일을 취합하고 엑셀로 정리해 입력하는 과정에서 자료 중복·누락과 잘못 전달된 자료를 확인해야 했습니다.
  • EDI 작업은 여러 메뉴에 흩어져 있었고, 입력값이 틀렸는지 원본 자료에 문제가 있는지 확인하려면 자료를 다시 대조해야 했습니다. 매출자료에서는 같은 제품코드 오류가 여러 업체에 반복됐습니다.

산출물 샘플: 화면 단위 PRD 구조

재구성 샘플 · 개별 정책의 근거는 위 PRD·결정로그 발췌를 확인하세요.

개요 → 범위 → 요구사항 → 화면 목적 → 개념 정의 → 시나리오 → 정책 → 데이터·연동 → 필드 상세 → 미결

화면 식별자(SCR-ID)를 기준으로 요구사항·정책·필드·미결 사항을 묶고, 고객 요청과 기획자의 해석·제안을 출처로 구분하는 구성입니다.

프로토타입·외부 API 검증과 등록 정책

화면 동작과 실제 연동은 나눠 확인

프로토타입에서는 등록·수정·권한·입력값의 정상 동작 조건을 정했습니다. AI가 브라우저를 조작해 입력·클릭과 결과를 확인하는 방식과 제가 직접 눌러보는 방식을 함께 사용하고, 실패한 부분은 수정 후 다시 확인했습니다.

국세청 API를 직접 호출해 사업자 상태와 응답 데이터를 확인하고, 개발자의 테스트 결과를 함께 검토했습니다.

외부 조회 데이터를 등록 흐름과 상태 정책으로 연결

병의원·약국 등록에서 외부 조회값을 자동 입력하는 경로와 조회 결과가 없을 때 직접 입력하는 경로를 나눴습니다. 외부의 개폐업 상태는 ERP 내부의 활성·비활성 상태와 구분했습니다.

  • 조회값이 있는 경우 외부 조회값을 등록 화면에 자동 입력
  • 조회 결과가 없는 경우 수기 입력 경로 제공
  • 폐업으로 확인된 경우 상태를 안내하는 창을 표시하고 신규 등록을 제한
  • 상태 표시 개폐업 상태와 내부 활성·비활성 상태를 별도로 관리
