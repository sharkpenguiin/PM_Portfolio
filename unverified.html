01 · 판단할 문제

등록되지 않았거나 값이 같아도,
잘못된 자료라고 단정할 수 없었습니다.

실제 거래 중인 약국도 정보 미갱신으로 미등록 상태일 수 있었습니다. 날짜·제품·약국·수량이 같아도 실제 중복이라고 단정할 수 없었습니다.

02 · 미등록 정보

가등록으로 보관하고,
확인 전에는 사용을 보류했습니다.

명칭·사업자번호·주소를 받아 임시로 보관하되, 담당자가 확인해 확정하기 전까지 거래 처리 화면에 노출하지 않도록 설계했습니다.

03 · 중복 의심

자동으로 지우지 않고,
확인할 대상으로 표시했습니다.

같은 값의 행을 바로 삭제하면 실제 중복이 아닌 자료도 사라질 수 있습니다. 시스템은 의심 표시를 하고, 담당자가 실제 중복 여부를 판단하도록 나눴습니다.

확인한 결과

고객사·디자인 리뷰를 거쳐
처리 흐름을 확정했습니다.

가등록 필수값과 처리 흐름을 확정하고, 결정로그에 “중복은 의심으로만 표시”로 남겼습니다. 중복 의심 표시 기준과 변경 로그·수정 사유 입력 방식은 후속 논의로 남았습니다.

미확정 매출자료 처리

확인되지 않은 자료는 시스템이 단정하지 않도록 설계했습니다.

  • 본인 역할확인 대상 처리 방식 설계
  • 기획 범위ERP·협력사 포털, 18개 업무 영역 단독 기획
  • 진행 상태리뷰 확정

미등록 정보와 중복 의심 자료를 나눠 사람이 확인하도록 설계했습니다.

  1. 01상황과 문제미등록이나 같은 값만으로는 확정·삭제할 수 없었습니다.
  2. 02해결가등록과 의심 표시로 나눠 사람이 확인하도록 설계했습니다.
  3. 03결과고객사·디자인 리뷰를 거쳐 확정했습니다.
01

상황과 문제

확인한 상황확인되지 않은 매출자료

  • 실제 거래 중인 약국도 정보가 갱신되지 않아 미등록으로 나타날 수 있었습니다. 미등록 약국은 신생 약국일 수도 있습니다.
  • 날짜·제품·약국·수량이 같아도 실제 중복이라고 단정할 수 없었습니다.
02

해결

마스터에 없거나 값이 같다는 이유만으로 확정·삭제하지 않고, 미등록 정보와 중복 의심 자료를 나눠 확인하도록 설계했습니다.
